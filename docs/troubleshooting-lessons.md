# 故障案例与工程教训

本项目开发与使用过程中真实踩过的坑。每条都给出：现象 → 根因 → 修复 → 教训。做同类审批 hook 时可直接对照排障。

## 案例 1：hook 脚本崩溃 → 所有操作"卡死"

**现象**：某次给脚本加诊断日志后，所有需要审批的操作全部回落人工弹窗，用户感知为"全都卡住"。

**根因**：新加的一行日志写在了变量声明**之前**（`log(...JSON.stringify(input)...)` 在 `const input = readStdin()` 之前），触发 TDZ ReferenceError，脚本每次调用即崩溃、无输出 → ZCode 回落人工。

**教训**：

- hook 脚本的一次崩溃 = 全部审批通道瘫痪（fail-to-human 的代价）
- **改 hook 脚本后必须先 `node --check` + 手动模拟调用（echo JSON | node 脚本）验证，再交付依赖它工作**
- 自救手段：切 Full access 模式（不发审批请求）让 AI 修复脚本；或人工点一次"允许"放行修复操作

## 案例 2：cwd 漂移 → 项目内路径被大面积误判"工作区外"

**现象**：某长会话后期，项目内路径（子目录、甚至项目根）被持续误判为"工作区外"，Write/Edit/bash/git 写入全部被拒；呈"正常窗口 ↔ 恶化窗口"交替，同一操作结果不稳定，耗时约 40-50 分钟。

**根因链**（日志取证确认）：

1. ZCode 传入的 `cwd` 是**动态当前目录**，会随 shell 的 `cd` 漂移到子目录（如 `project\tmp\extract`）；`ZCODE_PROJECT_DIR` 环境变量实测同样跟随漂移。协议中**没有稳定的"会话工作区根"**
2. 本地快路径依赖 cwd → 漂移后不再命中 → 落到模型判定
3. 给模型的"工作区根"同样是漂移值 → **模型在它看到的错误前提下做出了自洽的判断**（把项目根判为"工作区外"），且理由与本地事实矛盾
4. cwd 偶尔漂回项目根时一切正常 → 这解释了"窗口交替"与"判定不稳定"的假象

**修复**（三层）：

- `findProjectRoot()`：从 cwd / 环境变量**向上搜索最近的含 `.git` 或 `AGENTS.md` 的祖先目录**作为项目根，纳入工作区根集合
- **机械复核护栏**：模型以"路径越界"为由拒绝时，本地比对 `file_path` / 命令中的绝对路径，证实全部在工作区内则推翻误判（含外发/破坏特征的命令不享受复核）
- git 本地操作（add/commit/status/…）0ms 快路径——git 备份这类高频安全操作不应被审批误伤

**教训**：

- **cwd 与项目目录环境变量都是动态值，任何时候不能当稳定的边界依据**；可靠锚点是向上搜索项目标记目录
- **对模型的事实性断言（"路径在工作区外"）必须本地机械复核**——模型只掌握 hook 传入的信息，输入失真时它会给出"自洽但错误"的判定
- 误判发生时，**先怀疑输入数据失真，再怀疑模型能力**。在 hook 里记录每次调用的原始输入（尤其 cwd 与环境变量），几秒就能定位

## 案例 3："转人工"等于"挂起等人"

**现象**：早期设计里，模型拿不准（ESCALATE）、API 超时/故障时都不输出 → ZCode 弹人工窗。用户反馈"卡住"——命令长期不执行。

**根因**：人工弹窗会**无限期挂起等待**；而超时上限当时设了 45 秒 + 重试，最坏情况用户要等一分半才见到弹窗，且弹窗本身不知道何时会被处理。

**修复**：

- 模型改为 **ALLOW/DENY 二分类，拿不准一律 DENY**（立即返回、附理由、可重试）
- 超时压到 10 秒 + 1 次自动重试；重试仍失败 → 保守 deny + "审批服务暂时不可用，稍后重试"
- 全链路只保留一种"转人工"：审批服务未配置（缺 key）——让配置问题可见

**教训**：**"转人工"不是免费的兜底**，它会以"卡住"的形式被用户感知。审批系统的失败语义应该像判例法：宁可 DENY（有明确理由、可重试），不要挂起。

## 案例 4：模型会被内容字样干扰

**现象**：编辑一个工作区内文件时被判 DENY，理由是"写入工作区外路径"——而该文件明明在项目根。

**根因**：**文件内容里包含敏感路径字样**（如用户目录、"工作区外"等措辞），模型的判断被内容带偏；另一例是 heredoc 正文含某路径字样时被判"生成到外部目录"。

**修复**：工作区内 Write/Edit 走本地快路径（纯前缀比对，天然免疫内容干扰）；Bash 命令里的绝对路径靠机械复核兜底。

**教训**：**让模型判断路径事实是不可靠的**——它会被参数里的文本内容带偏。路径是否在工作区内是纯机械问题（字符串前缀比对），应该代码做；模型只该做机械判据之上的增量风险判断（这条命令想干什么、有没有外发/破坏意图）。

## 案例 5：弹窗闪现（竞速）

**现象**：自动审批工作正常，但每次仍能看到弹窗一闪而过。

**根因**：ZCode 的审批弹窗与 hook 判定**并发**——弹窗先渲染，hook 结果到达后自动关闭；判定耗时即弹窗停留时间。属 UI 机制，hook 侧无法完全消除。

**缓解**：把高频操作（工作区内编辑、只读命令、git 备份）放进 0ms 本地快路径后，日常使用基本见不到弹窗。给审批模型选快档（约 1 秒）也能显著缩短闪现。

## 附录：诊断方法沉淀

- **ZCode 自身日志不可靠**：`~/.zcode/cli/log/` 只有 turn.phase 级别的 hooks 痕迹，成功的 hook 执行不一定有记录。可靠做法是 hook 脚本内写本地日志（时间、原始输入、判定结果、耗时、依据）
- **手动模拟调用**是第一诊断手段：`printf '%s' '<json>' | node approval-hook.mjs`，直接看原始输出
- **记录原始输入**：日志里保留 cwd、环境变量探针（如 `env[ZCODE_PROJECT_DIR=...]`）和工具参数快照，工作区类问题一眼可见
- 连续误拒 2-3 次即停止试探、查看日志定位——不要无限重试硬闯，也不要用"改写命令外观"的方式骗过审批（当审批理由是事实错误时，规避表象会演变为规避安全机制本身）
